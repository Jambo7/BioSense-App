1. Purpose
1.1 Objective
This specification defines the engineering architecture of the Dynamic Health Model (DHM).
The DHM is the central intelligence object of the BioSense platform.
Every personalised decision made by BioSense shall ultimately originate from, update, or reference the Dynamic Health Model.
Where the BioSense Intelligence Constitution defines the philosophy governing the Dynamic Health Model, this document defines the engineering requirements necessary to implement it.
This specification is intended for software engineers, AI engineers, solution architects and future technical contributors responsible for building or maintaining the BioSense Intelligence Engine.

1.2 Scope
This document defines:
The purpose of the DHM 
Internal architecture 
State management 
Belief representation 
Update mechanisms 
Confidence storage 
Versioning 
Learning behaviour 
Relationships with other BioSense engines 
Engineering rules 
Acceptance criteria 
This document deliberately excludes:
Database implementation 
Programming language 
Infrastructure 
APIs 
Prompt engineering 
User Interface 
Deployment architecture 
Those subjects are covered by separate engineering specifications.

1.3 Authority
The Dynamic Health Model is governed by the BioSense Intelligence Constitution.
If any implementation conflicts with the Constitution:
The Constitution always takes precedence.

2. Design Philosophy
2.1 Core Principle
The Dynamic Health Model is not a database.
It is not a cache.
It is not a patient record.
It is BioSense's living representation of everything it currently believes about one individual.
That distinction governs every engineering decision contained within this specification.

2.2 Engineering Definition
For engineering purposes, the Dynamic Health Model is defined as:
A continuously evolving, version-controlled, evidence-backed belief system representing BioSense's current understanding of an individual's health.
Every word matters.
Continuously evolving
The DHM is updated after every meaningful interaction.
Version-controlled
Historical understanding must remain recoverable.
Evidence-backed
Every belief must be traceable to supporting evidence.
Belief system
The DHM stores interpretations, not merely observations.
Current understanding
The DHM always represents BioSense's latest validated understanding.

2.3 Why the DHM Exists
Without a Dynamic Health Model, every interaction becomes independent.
The AI would repeatedly analyse isolated observations without retaining meaningful understanding.
The DHM prevents this.
It enables BioSense to:
remember, 
learn, 
personalise, 
identify trends, 
revise beliefs, 
improve recommendations, 
improve confidence, 
become progressively more useful over time. 
The DHM therefore transforms BioSense from a reactive analysis tool into a longitudinal health intelligence system.

3. Architectural Position
The DHM occupies the centre of the BioSense Intelligence Engine.
Every subsystem contributes to it or consumes information from it.
Conceptually:
 Wearables ─────────────┐
 Blood Analysis ────────┤
 Nutrition ─────────────┤
 Daily Check-In ────────┤
 Medical Records ───────┤
 Learning Mode ─────────┤
 Conversation Engine ───┤
                         ▼
              Dynamic Health Model
                         │
         ┌───────────────┼────────────────┐
         ▼               ▼                ▼
 Health Score     Biological Age   Recommendation Engine
         ▼               ▼                ▼
       Reports      Notifications     AI Conversations
The Dynamic Health Model is therefore the single source of personalised intelligence within BioSense.
No subsystem should maintain its own independent interpretation of the user's health.

4. Engineering Principles
Every implementation of the Dynamic Health Model shall satisfy the following principles.

Principle 1 — The DHM Stores Beliefs, Not Facts
Observations are stored separately.
The DHM stores BioSense's interpretation of those observations.
Example:
Observation
Ferritin = 24 µg/L.
Belief
"The individual demonstrates a sustained decline in iron stores."
These are fundamentally different.
The Observation Store preserves objective truth.
The DHM preserves interpreted understanding.

Principle 2 — Every Belief Requires Evidence
No belief may exist without supporting evidence.
Every belief must maintain references to:
originating observations, 
supporting observations, 
scientific rationale, 
confidence, 
creation date, 
latest review, 
revision history. 
A belief without traceability is constitutionally invalid.

Principle 3 — History Is Never Destroyed
The DHM evolves.
It never overwrites previous understanding.
Whenever a belief changes:
the previous version remains archived, 
the reason for change is recorded, 
the new belief becomes active. 
This creates a complete audit trail.

Principle 4 — Confidence Belongs to Beliefs
Confidence is never attached to raw observations.
Raw observations simply exist.
Confidence describes BioSense's certainty in its interpretation.
Example:
Observation:
Resting Heart Rate = 61 bpm.
Confidence:
None.
Belief:
"The individual's cardiovascular recovery has improved."
Confidence:
87%.

Principle 5 — The DHM Learns Continuously
Every meaningful interaction is evaluated.
Possible outcomes include:
Create a new belief. 
Strengthen an existing belief. 
Weaken an existing belief. 
Retire an obsolete belief. 
Increase confidence. 
Decrease confidence. 
Make no change. 
"No change" is a valid engineering outcome.

Principle 6 — Silence Is Valid
Not every new observation changes understanding.
For example:
A single poor night's sleep may update the Observation Store but produce no change to the DHM because it does not materially alter BioSense's long-term understanding.
This prevents unnecessary volatility.

Principle 7 — One User, One Model
Every user has exactly one Dynamic Health Model.
All reasoning engines interact with this single model.
No subsystem shall maintain competing versions of user understanding.
This guarantees consistency across the platform.

5. Acceptance Criteria (Chapter 1)
This chapter shall be considered correctly implemented when:
The DHM is recognised as a belief system rather than a data store. 
Every engineer can distinguish observations from beliefs. 
Every belief is evidence-backed and traceable. 
Historical versions are preserved. 
Confidence is associated only with interpreted understanding. 
Every subsystem references the same Dynamic Health Model. 
The Constitution remains the governing authority for all implementation decisions.
Chapter 2
Canonical Structure of the Dynamic Health Model

2.1 Purpose
The purpose of this chapter is to define the canonical internal structure of the Dynamic Health Model (DHM).
The DHM represents BioSense's complete understanding of an individual at a given moment in time.
Every subsystem interacting with BioSense shall read from, write to, or reference this structure.
The DHM shall remain implementation-independent.
Whether stored in relational databases, graph databases, document stores or future technologies, the logical structure defined within this specification shall remain unchanged.

2.2 Design Objectives
The structure of the DHM shall satisfy the following objectives:
Represent current understanding. 
Preserve historical evolution. 
Support explainable reasoning. 
Enable continuous learning. 
Allow confidence tracking. 
Separate observations from interpretation. 
Support future expansion without redesign. 
Remain understandable by engineers and clinicians. 

2.3 Architectural Overview
Conceptually, the Dynamic Health Model consists of multiple interconnected domains rather than one flat record.
Dynamic Health Model
│
├── Identity
├── Observation References
├── Health Beliefs
├── Health Hypotheses
├── Health Narratives
├── Biological Identity
├── Goals
├── Confidence Layer
├── Recommendation History
├── Learning History
├── User Preferences
├── Audit Trail
└── Version Metadata
Each domain serves a distinct engineering purpose.
No domain should duplicate information already represented elsewhere.

2.3a Object Specification Convention
Every domain object in this chapter is described by attribute names only. Names are not an implementable schema. A normative Data Dictionary shall therefore accompany this specification and define, for every attribute of every object, its data type, cardinality (1:1 or 1:N), whether it is required, its permitted value set, and an example.
Until that dictionary is ratified the following conventions are binding: identifiers are opaque strings; dates are ISO-8601 timestamps; any attribute named 'Evidence', 'Supporting …' or 'Related …' is a list of typed references, each carrying the referent's object type and version, never free text; and 'Confidence Score' denotes the structured Confidence Object of Chapter 10, not a bare number.
Engineering Rule
No object may be implemented from attribute names alone. An attribute with no Data Dictionary entry has no defined type and shall not be relied upon across engines.

Constitutional Principle
Facts live in the Observation Store. Understanding lives in the DHM.

2.5a Observation Reference Integrity
References into the Observation Store are pinned to an immutable observation version, so a belief's cited evidence cannot change silently beneath it. Observations are corrected by appending a new version, never by mutating an existing one.
When an observation is corrected, superseded or withdrawn — including user correction (5.10) and any right-to-erasure deletion — every belief, hypothesis and narrative that references it shall automatically enter review (4.7, 5.12a). Erasure removes the referent's content while preserving a reference shell and an audit record that erasure occurred, so dependent reasoning is re-evaluated rather than left resting on evidence that no longer exists.
Engineering Rule
A belief may never reference an observation version that can change. If a referent is withdrawn, dependent beliefs are reviewed — never silently retained.

2.17a Relationship Ownership & History Boundaries
The 'no duplication' objective (2.3, 2.18) forbids two writable copies of the same fact, not relationships. For every relationship, exactly one side is authoritative (the owning side) and the inverse is derived, not independently edited. For belief↔narrative, the narrative's 'Supporting Beliefs' list is authoritative and a belief's 'Linked Narratives' is its derived inverse.
The three historical records serve distinct, non-overlapping purposes and shall not copy one another: a per-object Revision History records how a single object changed; the Learning History (2.13) records DHM-level state transitions; the Audit Domain (2.15) records who, what and which versions performed each change for governance. Where they concern the same event they reference it, they do not duplicate it.
Engineering Rule
Every relationship names its owning side; inverse links are computed, never separately maintained.
2.18 Engineering Constraints
The Dynamic Health Model shall:
avoid duplicated information, 
separate observations from beliefs, 
preserve version history, 
support explainability, 
support future domains, 
remain extensible, 
remain model-independent. 
No subsystem may modify the DHM outside the update rules defined later in this specification.

On Acceptance Criteria
Acceptance criteria throughout this specification shall be expressed as objective, automatable assertions, not comprehension goals. 'Every engineer understands the structure' is an onboarding aim, not a test. Each criterion should be restated in verifiable form — for example, 'the schema validator accepts a conformant object and rejects one missing a state-required attribute', or 'a cascade over the dependency graph provably terminates within CASCADE_MAX_DEPTH'.
Engineering Rule
A criterion that cannot be checked by a test or a defined inspection is not an acceptance criterion. This applies to the acceptance sections of every chapter.
2.19 Acceptance Criteria
This chapter shall be considered complete when:
✓ Every engineer understands the logical structure of the DHM.
✓ Every domain has a clearly defined purpose.
✓ No information is duplicated unnecessarily.
✓ Raw observations remain separated from interpreted understanding.
✓ The model supports continuous learning.
✓ Every belief, narrative and recommendation is traceable.
✓ Future domains can be added without redesigning the architecture.
Chapter 3
State Transitions & Update Lifecycle

3.1 Purpose
The purpose of this chapter is to define the constitutional lifecycle governing every modification made to the Dynamic Health Model (DHM).
The DHM shall never be modified directly.
Instead, every modification shall occur through a controlled update lifecycle that preserves:
explainability, 
traceability, 
version history, 
scientific integrity, 
constitutional compliance. 
This ensures every change to BioSense's understanding can be reconstructed, explained and audited.

3.2 Design Philosophy
The Dynamic Health Model is not edited.
It evolves.
Every new observation is treated as an opportunity to improve understanding rather than overwrite previous knowledge.
Consequently, every update shall represent a transition between two clearly defined belief states.

Constitutional Principle
The DHM never jumps. It transitions.

Engineering Rule
No DHM update may occur without a recognised trigger. This section is the single canonical trigger registry: every trigger referenced elsewhere in this specification — including Scientific Library updates (5.3, 5.9) and the Scheduled Review trigger (3.3a) — shall be listed here and shall not be introduced independently in another chapter.

3.3a Scheduled Review Trigger & Time-Based Decay
Confidence and memory decay over time without new evidence (5.11, 6.12, 10.8), so time itself is a recognised trigger. The canonical registry (3.3) therefore includes a Scheduled Review trigger: a periodic, system-generated event, per individual and per object class, under which the Confidence Engine re-evaluates ageing beliefs and confidence objects.
Decay shall be implemented one way platform-wide, not mixed: either eagerly (the Scheduled Review trigger writes a new version when decay changes a value) or lazily (decay is computed at read time and materialised on the next genuine update). Decay rate is DECAY_HALF_LIFE per object class (value to be confirmed).
Engineering Rule
This reconciles 3.3 ('no update without a trigger') with time-based decay: the passage of time is expressed as the Scheduled Review trigger, never as an untriggered mutation.

3.5 Types of State Transition
Every update shall result in one or more transition types, all committed together within a single reasoning session (see 3.12a). A session that merges several triggers, or that cascades across dependent beliefs, may legitimately produce several transition types within one atomic commit.

Type 1 — No Change
New evidence does not materially alter BioSense's understanding.
Examples:
One poor night's sleep.
Small HRV fluctuation.
Single workout.
Temporary travel disruption.
Outcome:
Observation stored.
DHM unchanged.

Constitutional Principle
New information does not always create new understanding.

Type 2 — Confidence Strengthened
Understanding remains unchanged.
Confidence increases.
Example:
Existing belief:
Recovery improves with 8+ hours of sleep.
Three further observations support it.
Belief unchanged.
Confidence increases.

Type 3 — Confidence Reduced
Contradictory evidence weakens confidence.
The belief remains active.
Further evidence required.

Type 4 — Belief Updated
Existing understanding evolves.
Example:
Initial belief:
Sleep consistency is improving.
Updated belief:
Sleep consistency has plateaued.

Type 5 — New Belief Created
New evidence supports an entirely new understanding.
Example:
Repeated blood tests reveal progressive iron depletion.
A new Health Belief is created.

Type 6 — Belief Retired
Existing understanding is no longer supported.
Example:
A previously suspected inflammatory pattern disappears after twelve months of normal biomarkers.
The belief is retired.
Historical versions remain archived.

Type 7 — Narrative Updated
Multiple beliefs combine to alter a higher-level Health Narrative.
Example:
Recovery.
Sleep.
Training.
Nutrition.
Together produce a new Recovery Narrative.

Type 8 — Biological Identity Updated
The slowest transition.
Requires prolonged evidence.
Examples:
Exercise resilience.
Sleep chronotype.
Stress resilience.
Recovery profile.
These should change rarely.

3.6 Belief Promotion
Not every hypothesis becomes a belief.
Promotion requires:
sufficient evidence, 
scientific plausibility, 
repeated validation, 
constitutional review. 
Only then may a hypothesis enter the Health Belief Domain.

Engineering Rule
Hypotheses shall never bypass promotion rules.

3.6a Constitutional Thresholds Are Named Parameters
Wherever this specification states a qualitative decision boundary — 'sufficient evidence', 'prolonged evidence', 'materially', 'significantly', 'overwhelming' — that boundary shall be implemented as a named, versioned configuration parameter owned by the clinical/data-science function, never hard-coded and never left to individual engineer judgement.
Parameters requiring definition include PROMOTION_MIN_OBSERVATIONS and PROMOTION_MIN_TIMESPAN (hypothesis → belief, 3.6); IDENTITY_STABILITY_WINDOW (Biological Identity change, 2.9); DEPENDENT_REVIEW_DELTA (when a weakened supporting belief forces dependents into review, 4.7); and MATERIAL_CHANGE_THRESHOLD (Type 1 'No Change' versus a real transition, 3.5). The values are to be confirmed; the parameters themselves are binding now.
Engineering Rule
A qualitative threshold with no named parameter is unspecified behaviour and shall block implementation of the affected rule.

Engineering Rule
Contradictory evidence delays certainty.
It never bypasses reasoning.

3.11 Atomic Updates
A DHM update shall be atomic.
Either:
The complete update succeeds.
Or:
No update occurs.
Partial updates are constitutionally prohibited.
This prevents inconsistent belief states.

3.12 Concurrent Events
Multiple trigger events may occur simultaneously.
Example:
Blood test uploaded.
Wearable synchronised.
Learning Mode completed.
The Intelligence Engine shall merge these into a single reasoning session before updating the DHM.
The user should possess one coherent understanding.
Not three independent updates.

3.12a Concurrency & Session Model
Concurrency is resolved per individual. All trigger events for one individual are processed by a single-writer reasoning session; sessions for different individuals run in parallel. This makes 'atomic' (3.11) well defined — the session is the transaction — and removes belief-state races without global locking.
Triggers for an individual are enqueued. A session opens on the first queued trigger and admits further triggers arriving within a bounded merge window (SESSION_MERGE_WINDOW, value to be confirmed). Triggers arriving after the window are handled by the next session and never mutate a session already in progress.
One session produces exactly one new DHM version (3.9), which may contain several transition types (3.5) together with the results of any cascade (5.12a). Either the whole session commits or none of it does (3.11).
Engineering Rule
No two sessions may write the same individual's DHM concurrently. Isolation is serialisable per individual. The session's atomicity is scoped to the DHM. Writes to stores owned by other engines (Decision, Prediction, Safety) occur outside this session and are coordinated by ENG-009 under its cross-store consistency boundary (ENG-009 §6.7a).
3.13 Learning Without Communication
Some updates shall remain invisible.
Example:
Confidence increases.
Internal relationships strengthen.
Biological Identity matures.
No user-facing communication required.
Learning and communication remain independent processes.

Founder Principle
The DHM may become wiser without becoming louder.

3.14 Rollback
If a critical implementation error is discovered, BioSense shall restore the previous DHM version without data loss.
Rollback shall preserve:
Original observations.
Historical versions.
Audit records.
Reason for rollback.
Rollback shall never delete historical reasoning.

3.15 Engineering Constraints
Every state transition shall:
preserve history, 
preserve traceability, 
preserve explainability, 
maintain constitutional compliance, 
remain deterministic in retrieval, versioning and rule evaluation (generative summaries excepted),
support future AI models, 
remain implementation independent. 

3.16 Acceptance Criteria
This chapter shall be considered complete when:
✓ Every DHM modification follows one recognised lifecycle.
✓ Every update creates a traceable version.
✓ Beliefs never change without evidence.
✓ Contradictory evidence is evaluated rather than ignored.
✓ Learning may occur without communication.
✓ Historical reasoning remains recoverable.
✓ Updates are atomic and auditable.
Chapter 4
Belief Engine & Knowledge Representation

4.1 Purpose
The purpose of the Belief Engine is to transform validated observations into structured, explainable knowledge that can be used consistently throughout the BioSense Intelligence Engine.
The Dynamic Health Model does not store isolated observations.
Nor does it store arbitrary AI-generated text.
Instead, it stores a structured collection of Health Beliefs, each representing a specific element of BioSense's current understanding.
The Belief Engine governs how these beliefs are created, strengthened, weakened, connected and retired.
It is the core mechanism through which BioSense develops understanding over time.

4.2 Engineering Philosophy
The Intelligence Engine shall reason using explicit knowledge objects rather than transient conversations.
Every important conclusion reached by the Intelligence Engine should exist as a reusable belief within the DHM.
This ensures that understanding becomes persistent rather than being recreated every time the AI is queried.
The Belief Engine therefore separates:
reasoning, 
storage, 
communication. 
Reasoning creates beliefs.
The DHM stores beliefs.
The Conversation Engine communicates beliefs.
These responsibilities shall remain independent.

Constitutional Principle
Reason once. Reuse understanding everywhere.

4.3 What Is A Health Belief?
A Health Belief is the smallest reusable unit of understanding within the Dynamic Health Model.
It represents an interpreted conclusion that has survived constitutional reasoning.
Examples include:
Sleep consistency is below the individual's long-term baseline. 
Cardiovascular recovery has improved over the past three months. 
Ferritin has shown a sustained downward trajectory. 
Evening alcohol consistently reduces HRV. 
Recovery improves when protein intake exceeds 140g/day. 
Health Beliefs are not observations.
They are not recommendations.
They are BioSense's current understanding.

Engineering Rule
A belief missing an attribute that is mandatory for its current lifecycle state shall be considered invalid. Requiredness is conditional on state (see 4.4a and the Data Dictionary): a Candidate belief need not carry Confidence History, Last Reviewed or a Retirement Reason, whereas a Validated belief requires supporting evidence and a Retired belief requires a Retirement Reason.

The Health Belief illustrates the Data Dictionary format (2.3a) every object shall follow — field, type, cardinality, requiredness:

retirement_reason — string — 0:1 — required only when status = Retired.
Engineering Rule
Every object in this specification shall be accompanied by a schema of this form before it is implemented.
4.5 Belief Categories
To ensure consistency, every belief shall belong to one primary category.
Trend Beliefs
Describe long-term physiological movement.
Examples:
Improving. 
Declining. 
Stable. 
Fluctuating. 

Behavioural Beliefs
Describe relationships between behaviour and physiology.
Examples:
Sleep improves recovery. 
Late caffeine delays sleep onset. 
Resistance training improves glucose control. 

Physiological Beliefs
Describe the individual's current biological state.
Examples:
Low iron stores. 
Elevated inflammatory profile. 
High cardiovascular fitness. 

Predictive Beliefs
Represent expectations about future physiology.
Examples:
Recovery is likely to decline during travel. 
Seasonal allergy patterns expected next month. 
Predictive beliefs shall always carry explicit uncertainty.

Identity Beliefs
Describe stable characteristics of the individual.
Examples:
Morning chronotype. 
High exercise responder. 
Slow recovery following international travel. 
Identity beliefs require the strongest evidence.

Assess evidence quality. 
Generate alternative hypotheses. 
Reduce confidence if required. 
Escalate for constitutional review. 
The DHM should never knowingly contain unresolved contradictions.

Founder Principle
Conflicting beliefs are signals for investigation, not errors to ignore.

Chapter 5
Belief Revision & Evidence Reconciliation

5.1 Purpose
The purpose of this chapter is to define the engineering rules governing how the Dynamic Health Model revises its understanding when new evidence becomes available.
The Dynamic Health Model shall never assume that its current understanding is permanently correct.
Instead, every Health Belief shall remain open to revision throughout its lifecycle.
The Belief Revision Engine exists to ensure that BioSense continuously improves its understanding while preserving scientific integrity, historical explainability and user trust.

5.2 Design Philosophy
Understanding is not static.
It evolves.
Every new observation should be treated as an opportunity to ask:
"Does this change what we currently believe?"
Sometimes the answer will be:
No.
Sometimes:
Slightly.
Occasionally:
Completely.
The purpose of the Belief Revision Engine is to determine which of these outcomes is constitutionally justified.

Constitutional Principle
Every belief remains provisional until supported by overwhelming long-term evidence.

5.3 Triggers for Belief Review
A belief review may be initiated by any event capable of materially changing BioSense's understanding.
Examples include:
New blood biomarkers. 
Wearable trends. 
Learning Mode responses. 
Goal changes. 
Medical records. 
Repeat laboratory testing. 
Recommendation outcomes. 
User corrections. 
Updates to the Canonical Scientific Library. 
New scientific evidence. 
Not every trigger will result in revision.
Every trigger shall result in evaluation.

Engineering Rule
Belief review is mandatory.
Belief revision is optional.

5.4 The Belief Revision Lifecycle
Every review shall follow the same constitutional sequence.
Existing Belief
       │
       ▼
Receive New Evidence
       │
       ▼
Validate Evidence
       │
       ▼
Assess Evidence Quality
       │
       ▼
Compare Against Existing Belief
       │
       ▼
Generate Alternative Explanations
       │
       ▼
Review Confidence
       │
       ▼
Select Outcome
       │
       ▼
Update Dynamic Health Model
No shortcut shall bypass this lifecycle.

5.5 Possible Revision Outcomes
Every review shall result in one of the following outcomes.

Outcome A
No Change
Existing understanding remains the strongest explanation.
The new observation is stored.
Confidence remains unchanged.
Example:
One isolated poor night's sleep.

Outcome B
Confidence Increased
New evidence strengthens an existing belief.
The wording remains unchanged.
Only confidence increases.
Example:
Another six months of improving ferritin.

Outcome C
Confidence Reduced
The belief remains active.
However:
Competing evidence reduces certainty.
Further evidence becomes desirable.

Outcome D
Belief Refined
The underlying understanding remains valid.
Its wording becomes more accurate.
Example:
Original:
Recovery improves with longer sleep.
Updated:
Recovery improves primarily when sleep exceeds 7.5 hours for at least three consecutive nights.
Understanding becomes more precise.

Outcome E
Belief Replaced
A superior explanation emerges.
The original belief is archived.
A new belief becomes active.
Historical traceability remains preserved.

Outcome F
Belief Retired
Evidence no longer supports the belief.
The belief remains visible historically.
It is no longer active.

Founder Principle
Retiring a belief is evidence of learning, not failure.

5.6 Competing Beliefs
The Dynamic Health Model shall permit multiple competing explanations during periods of uncertainty.
Example:
Hypothesis A
Reduced recovery due to insufficient sleep.
Hypothesis B
Reduced recovery due to iron deficiency.
Hypothesis C
Reduced recovery due to illness.
Each hypothesis shall maintain independent confidence.
As new evidence emerges, confidence changes until one explanation becomes dominant.

Constitutional Principle
Uncertainty should be represented explicitly rather than hidden.

5.7 Contradictory Evidence
Contradictory evidence shall never be discarded simply because it disagrees with current understanding.
Instead, BioSense shall ask:
Is the new evidence reliable? 
Does it conflict with one belief or many? 
Is the conflict temporary? 
Has similar conflict occurred previously? 
Does this reveal a limitation in our current understanding? 
Contradiction should trigger investigation.
Not immediate replacement.

5.8 Evidence Accumulation
Individual observations rarely justify major revision.
Instead, the Belief Revision Engine shall evaluate cumulative evidence.
Examples:
One elevated CRP.
↓
Observation.
Three elevated CRP results over twelve months.
↓
Pattern.
Repeated elevation together with lifestyle and symptom changes.
↓
Belief revision.
Time strengthens evidence.

Founder Principle
Patterns revise beliefs. Isolated observations usually do not.

5.9 Scientific Revision
The Dynamic Health Model shall remain capable of revising beliefs even when the user's data has not changed.
Example:
New scientific evidence changes the accepted interpretation of a biomarker.
The Canonical Scientific Library updates.
Existing beliefs are re-evaluated.
This ensures BioSense evolves alongside modern medicine.

Constitutional Principle
Scientific progress should improve understanding without requiring new user data.

5.10 User Corrections
Users may challenge BioSense's understanding.
Examples:
"That wasn't iron deficiency."
"I had influenza that week."
"I wasn't wearing my wearable."
"I stopped taking that medication."
User corrections become evidence.
They do not automatically replace existing beliefs.
Instead they enter the revision process using the same constitutional rules as every other observation.

Engineering Rule
User feedback influences beliefs.
It does not bypass reasoning.

5.11 Confidence Drift
Confidence shall naturally change over time.
Without ongoing supporting evidence:
Confidence may gradually weaken.
With repeated confirmation:
Confidence may strengthen.
This prevents outdated understanding remaining permanently dominant.

5.12 Cascading Revision
Changing one belief may require reviewing others.
Example:
New evidence weakens:
Iron Deficiency.
This may also influence:
Recovery Narrative.
Fatigue Narrative.
Supplement Recommendations.
Health Score.
Biological Age.
The Belief Revision Engine shall automatically identify downstream dependencies.

Constitutional Principle
Beliefs exist within a network. Revision should respect that network.

5.12a Cascade Traversal Rules 
Belief dependencies form a directed graph. To make cascading revision (5.12, 4.7, 6.16) deterministic and terminating, the dependency graph shall be maintained as acyclic; any edge that would create a cycle is rejected and recorded for review rather than followed.
A cascade is evaluated in topological order over affected dependents, within the same reasoning session (3.12a). Each object is visited at most once per session; re-entry of an object already visited does not re-open it. Cascade depth is bounded by CASCADE_MAX_DEPTH (value to be confirmed); reaching the bound halts the cascade and raises a review flag rather than looping. A cascade never crosses individuals and never escapes the session's atomic commit.
Engineering Rule
Cascading revision shall always terminate. A cascade that cannot terminate within the configured bound is a defect, not a valid state.
5.13 Explainability
Every revision shall permanently record:
Previous belief.
Updated belief.
Reason for revision.
Supporting evidence.
Competing evidence.
Confidence change.
Trigger event.
Reviewer version.
Timestamp.
Every revision should therefore answer:
"Why did BioSense change its mind?"

5.14 Engineering Constraints
The Belief Revision Engine shall:
never overwrite historical understanding, 
preserve complete audit history, 
permit competing explanations, 
support scientific evolution, 
remain deterministic in retrieval, versioning and rule evaluation (generative summaries excepted),
remain explainable, 
remain independent of any AI provider. 

5.15 Acceptance Criteria
This chapter shall be considered complete when:
✓ Every belief can be reviewed.
✓ Every belief can be revised.
✓ Contradictory evidence is preserved.
✓ Historical beliefs remain recoverable.
✓ Confidence evolves naturally.
✓ User corrections enter the reasoning process.
✓ Scientific updates can trigger belief review.
✓ All revisions remain fully explainable.

New observations. 
Updated beliefs. 
Increased confidence. 
Genuine discoveries.

Not every belief update represents new knowledge.

Chapter 10
Confidence Engine & Confidence Architecture

10.1 Purpose
The purpose of the Confidence Engine is to quantify how strongly the Dynamic Health Model supports its current understanding.
Confidence is a constitutional concept.
It does not measure the confidence of a Large Language Model.
It does not measure the certainty of a prompt.
It measures the confidence BioSense has in its current interpretation of an individual's health, based upon all available evidence.
The Confidence Engine therefore exists to ensure that every belief, narrative, recommendation and prediction is proportionate to the quality of supporting evidence.

Constitutional Principle
Confidence belongs to understanding, not to the language model generating the response.

10.2 Engineering Philosophy
Confidence is not a single number.
It is a structured engineering object.
Every confidence assessment shall explain:
Why confidence exists. 
What evidence supports it. 
What evidence weakens it. 
What evidence would increase it. 
What evidence could reduce it. 
Confidence should therefore be explainable rather than opaque.

Engineering Rule

10.5a Confidence Computation Contract
Confidence is stored as a continuous score in the range 0 to 1 and is additionally classified into the six ordinal bands C0–C5 (10.4) by fixed, versioned thresholds. The continuous score is the source of truth; the band is a derived label for internal routing. 'Confidence Score' (4.4) refers to the continuous value; user-facing communication uses language, never either form (10.4).
The score is produced by a single, versioned function owned by the Confidence Engine that combines the nine inputs of 10.5. The function shall be monotonic and bounded, shall never exceed the strongest justifiable confidence of its inputs (10.7), and shall treat correlated physiological signals as non-independent — 'multi-source convergence' may raise confidence only where source independence is established. The combination method, the input weights, and the C0–C5 thresholds are configuration parameters requiring data-science and clinical sign-off before implementation.
Engineering Rule
Confidence is computed by exactly one function in one engine. No consumer may derive its own confidence, and no value may be produced without a recorded explanation of the inputs that generated it (10.13).

Different evidence sources may produce different confidence levels.

Constitutional Principle

Founder Principle

10.15 Engineering Constraints
The Confidence Engine shall:
remain deterministic in retrieval, versioning and rule evaluation (generative summaries excepted),
remain explainable, 
support versioning, 
support confidence propagation, 
support confidence decay, 
support calibration, 
support future evidence sources, 
remain independent of AI providers. 

10.16 Acceptance Criteria
This chapter shall be considered complete when:

Chapter 14

14.1 Purpose
The purpose of the DHM Query Engine is to define how every BioSense subsystem retrieves personalised understanding from the Dynamic Health Model.
The Dynamic Health Model is not a passive data store.
It is an active knowledge service.
Every subsystem interacting with the DHM shall request understanding rather than raw observations.
The Query Engine ensures that all consumers receive consistent, explainable and constitutionally compliant knowledge.

Constitutional Principle
Every BioSense engine should ask the Dynamic Health Model what it understands—not what data it possesses.

14.2 Engineering Philosophy
The DHM should never expose its internal complexity to consuming engines.
Instead, every consumer should receive:
validated understanding, 
relevant context, 
confidence, 
uncertainty, 
provenance. 
This creates a clean separation between:
knowledge formation,

Biological Identity changes. 
Freshness shall always take priority over performance.

Engineering Rule
Performance optimisation shall never compromise correctness.

14.8a Cache Scope & Invalidation
Cached understanding is keyed to the DHM version and to the specific subgraph a query depends on — its beliefs, narratives, discoveries, confidence objects and identity — not to the whole model. A commit invalidates only cache entries whose dependency subgraph intersects the objects that changed, rather than flushing the entire cache.
Engineering Rule
Invalidation is dependency-scoped, not global. Correctness still takes priority (14.8): if the dependency set of an entry cannot be determined, that entry is invalidated.
14.9 Permission Boundaries
Different consumers may receive different knowledge.
Examples:
Recommendation Engine
Full structured knowledge.

Conversation Engine
Human-readable understanding.

Analytics Engine
Aggregated anonymous insights only.

Future Clinical Portal
Extended explainability.
The Query Engine shall enforce access rules independently of the DHM.

14.9a Access-Control Model
Because the DHM holds special-category health data, access control is a defined subsystem, not an implementation detail. Each consumer is bound to a scope specifying which object types it may read, at what granularity (full structured knowledge, human-readable understanding, or aggregated anonymous only) and which fields are redacted. The Analytics scope receives only de-identified aggregates and never row-level beliefs, observations or identity.
Access is enforced at a single point — the Query Engine — before any knowledge leaves the DHM boundary, and every access is written to the Audit Domain (2.15). Scopes are versioned configuration; a consumer with no scope receives nothing.
Engineering Rule
No engine reads the DHM except through the Query Engine, and the Query Engine denies by default. Access rules are enforced independently of the reasoning that produced the knowledge.
14.10 Failure Handling
If required knowledge cannot be retrieved:
The Query Engine shall:
identify the missing dependency, 
preserve existing understanding, 
report the limitation, 
avoid fabricating conclusions. 
Incomplete retrieval shall reduce confidence.
It shall never generate false certainty.

Constitutional Principle
Failure to retrieve knowledge should reduce confidence—not invent understanding.

14.11 Engineering Constraints
The Query Engine shall:
expose understanding rather than raw data, 
remain deterministic in retrieval, versioning and rule evaluation (generative summaries excepted),
support explainability, 
support engine-specific responses, 
preserve provenance, 
enforce permissions, 
remain independent of AI provider.

Chapter 15
Governance, Auditability & Version Control

15.1 Purpose

The DHM represents the most valuable intellectual asset within BioSense.
Every modification to the DHM shall therefore be:
traceable, 
explainable, 
reproducible, 
version controlled, 
constitutionally compliant. 
Governance exists to ensure that BioSense remains trustworthy as it grows in complexity over many years.

Constitutional Principle
Trust requires that every important decision can be explained, reconstructed and independently verified.

15.2 Engineering Philosophy
The DHM shall never behave as a mutable profile.
Instead, it shall behave as a continuously versioned knowledge system.
At any point in time BioSense shall be capable of answering:
What did we believe? 
Why did we believe it? 
Which evidence supported it? 
Which version of the Intelligence Engine reached that conclusion? 
What changed since then? 
Governance therefore applies not only to data, but also to reasoning.

Engineering Rule
No meaningful change to the DHM shall occur without leaving a permanent audit record.

15.3 Governance Objectives
The governance framework shall ensure:
Full historical traceability. 
Complete explainability. 
Reproducible reasoning. 
Constitutional compliance. 
Safe evolution. 
Engineering accountability. 
Scientific transparency. 
Governance shall support both technical debugging and future clinical confidence.

15.4 Versioning Strategy
The Dynamic Health Model shall maintain multiple independent version histories.
These version histories shall evolve independently.

DHM Version
Represents the current state of the individual's understanding.
Incremented whenever the individual's understanding changes.

Constitution Version
Represents the constitutional framework governing reasoning.
Allows historical decisions to be interpreted within their original constitutional context.

Engineering Specification Version
Represents the engineering rules in force when reasoning occurred.
Supports long-term platform evolution.

Scientific Library Version
Represents the scientific evidence base used during reasoning.
Critical because scientific understanding evolves over time.

AI Model Version
Records the AI model(s) participating in reasoning.
Examples:
GPT-5.5 
Claude 
Gemini 
Future internal BioSense reasoning models 
The AI model shall never become the source of truth.
It is simply one component of the reasoning process.

Confidence Engine Version
Records which confidence algorithm generated confidence assessments.

Recommendation Engine Version
Records which recommendation logic generated interventions.

Engineering Rule
Independent version histories shall never be merged into a single version number.

15.4a Version Identifier Scheme
Each independent history uses a monotonic version identifier. The DHM version is not a number that embeds the others; it is a manifest that references the exact version of every constituent object (beliefs, narratives, confidence objects, identity) together with the Constitution, Engineering, Scientific Library, AI Model and Confidence Engine versions in force. Reconstructing 'the DHM at version N' means resolving that manifest.
Engineering Rule
A DHM version shall be resolvable to the precise set of object and framework versions that produced it; independent histories are never collapsed into a single number (15.4).
